# Plan: bridge skills `product-to-build` and `ship-to-content` (gaisser-agents 4.6.0)

## Handoff

### Goal
Add two bridge skills to the plugin. `product-to-build` takes a closed product-team run folder, splits the MVP into ordered slices with one software-team handoff each, waits for approval, then builds slice by slice with the software team's core flow. `ship-to-content` turns a merged PR, tag, commit range, or changelog into reviewed build-in-public drafts with the content team, with an explicit redaction step.

## Design decisions and trade-offs

1. **Where each skill lives.** `product-to-build` lives in `software-team`, `ship-to-content` in `content-team`: each sits in the team whose agents it runs, so every agent is a validated `{{agent:...}}` token rendered per tool, and nothing is borrowed. The other team's output is read as files. Rejected: product-to-build in `product-team` borrowing software agents by plain name (allowed by build.py, since borrowing is not limited to entry skills, but unvalidated and needing a name-exists test); a new `bridge-team` (a team needs an agent and an entry skill, and it would be empty); changing build.py to allow cross-team tokens (a schema change for no gain).
2. **Naming.** Bridge skills are named `<from>-to-<to>`. They are not entry skills, so the "one entry skill per team" rule stays; CONTRIBUTING gains a short bridge-skill rule.
3. **Relation to the product team (reuse).** product-to-build consumes the spec's `## Build handoff` (Goal and Constraints copied verbatim into every slice) and keeps the spec's AC IDs, which is the existing contract ("the architect must keep the AC IDs"). The product team's final report item 5 and its "never start building" rule now point to `product-to-build`; calling the software team directly with the spec stays valid for a one-slice plan.
4. **AC IDs.** Spec criteria keep their IDs and `(USn)` tags in the slice handoffs. Slice-only criteria (build, regression) get new IDs after the spec's highest ID, unique across slices. Tracing is then by ID, with no new field in the AC format. The architect may make a Check concrete but must never weaken a condition.
5. **Who slices.** The orchestrator slices and fills each handoff, like the software team does for build agents without an architect; Files to touch is marked provisional and the architect's plan settles it. Rejected: an architect "slicing mode" (prompt change and a second plan format).
6. **Plans per slice** go to `docs/product/<slug>/build/S<n>-plan.md`, not `docs/plan.md`, so slices do not overwrite each other and the trace stays in the run folder.
7. **ship-to-content reuses the content-team skill by sibling path** (`../content-team/SKILL.md`, its `assets/` and `references/`), applying its Project context, Run folder and state, Media policy, and Adapters sections unchanged. The plugin and both installers always ship every skill as siblings. Rejected: copying 5 templates and 7 references (drift); invoking the content-team skill wholesale (its Full run always runs a full scout and has no ship gate).
8. **Scout.** Light pass by default (new `## Light pass` in `scout-research.md`), full pass on request. Skipping the scout entirely is not offered, because the writer picks its hook from `scout.md`.
9. **Shipped-work claims** trace to `ship.md` evidence lines; this needs one conditional sentence in the writer and QA prompts and in `qa-checks.md` check 3. Without `ship.md`, nothing changes.
10. **Default format:** `post` (text plus one coded ship card) for a PR or commit range, because it is the cheapest piece to render and QA, fits every platform, and suits a frequent shipping cadence; `carousel` for a release, tag, or changelog with 3 or more user-visible changes. Video and thread only on request. Stated with its reason at the Ship gate.
11. **Redaction is layered:** raw diff and code never reach a subagent or the run folder; `ship.md` is written only after the R1-R8 checks; the user approves it at the Ship gate before any delegation; QA applies the checks in check 4; the orchestrator runs a leak scan before the review gate.

## Risks and edge cases

- `LEAK_RE` false positives in new text (PR numbers, hex-like words after `#`, home paths in examples). Mitigation: Constraints rule; AC17.
- Tests with hard-coded values break on this change: `test_modified_codex_plugin_file` (`4.5.0`), `test_change_with_bump_passes` (`4.5.1` would now be a downgrade), unchanged counts 29 and 31, `--list` skill regex. Step 7 updates them.
- Sibling path missing when a user copies one skill folder by hand: the skill checks for `../content-team/SKILL.md` and stops with "install the whole plugin".
- Product run edge cases: no run folder; spec without marker; `review.md` missing; verdict `open`; review older than the spec (stale); an MVP criterion with no slice; an existing `slices.md` (resume); a slice that fails twice (dependents are not started).
- Ship input edge cases: `gh` missing, unauthenticated, or offline (local git fallback); PR not merged; squash merge (find `(#<n>)` in subjects); empty range or unknown tag; a huge diff (stats and summaries only); a secret in the shipped history (never quoted; the final report tells the user to rotate it); repository visibility unknown (treated as private); co-author names (ask).
- The per-slice review gate will usually trigger (more than 3 files); this is intended, because the approval gate approves the slicing, not the plans.
